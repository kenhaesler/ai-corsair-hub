## 1. Summary

- **The "Device Control Service" is not what its name suggests.** The file in the iCUE dir, `Corsair Device Control Service.exe`, is a WiX **Burn installer bundle** (v1.9.9; strings `BurnPipe.%s`, `Burn v%1!hs!`, `pipe.cpp`) — it brokers nothing. The real service is `C:\Program Files\Corsair\Corsair Device Control Service\bin\CorsairDeviceControlService.exe` (SCM key `CorsairDeviceControlService`, currently Stopped/Disabled). It is a **DRAM/SMBus lighting service** (Dominator memory) using the `CorsairLLAccess64.sys` driver — no HID, no USB, no fans, no PSU. [OBS]
- The DCS *does* broker access, but only **between its own clients** (iCUE SDK / third-party lighting clients) via named pipe `\\.\pipe\CorsairUtilityEngine\…` with a handshake and a **client-priority arbitration** ("Clients priority changed: reject control for {} and allow control for {}"). `CorsairDeviceControlServiceAPI.dll` is its client library (`CDCSConnect`, `CDCSSetLightingPriority`, `CDCSSubscribeToDevicesChanged`, `CorsairSetLayerPriority`…). It refuses to run if service `CorsairLLAService` is present. [OBS]
- **.NET "clink" = legacy Corsair Link 4 stack, still shipped and run by iCUE 5** as Windows service `CorsairService` (`clink\Corsair.Service.exe`; internal name `CLinkIntegrationService`). The native iCUE app talks to it as a client over named pipe **`CLinkPipeService`** with JSON methods (`GetDevices`, `SetSensorSettings`, `LimitedSoftwareMode`, …). Native side: `modules\ClinkProto.dll`. [OBS]
- **HX1500i (PID 0x1C1F) is detected and driven by the .NET clink stack** (`DeviceTypeDetector` → `DeviceType.PowerSupply` → `PowerSupplyUnit`), not by a dedicated native driver. `devices\hx1500i.rcc` is only UI/manifest. The **iCUE LINK hub (0x0C3F) is NOT in any clink table** (grep of all decompiled sources: zero hits) → handled natively by iCUE. [OBS]
- clink detection is **two-pronged**: (a) **WMI** `SELECT * FROM Win32_PnPEntity WHERE DeviceID LIKE 'hid%'` for PSUs/Coolit/Robbins, PID parsed out of the PnP DeviceID string, re-enumerated on device-arrival events; (b) **HidSharp `HidDeviceLoader`** filtered by an explicit VID/PID list (Pro + Platinum families), 900 ms cache. Hotplug = `RegisterDeviceNotification` (all interface classes) + 250 ms Rx throttle → full re-enumeration. [OBS]
- **Conflict avoidance is cooperative, not exclusive.** HID files are opened `FILE_SHARE_READ|WRITE`, and opened/closed **per command**; all device I/O in the service is serialized by one process-wide semaphore plus `CorsairDevicesGuard`; a global named mutex `Global\Access_SMBUS.HTP.Method` guards SMBus; and a **registry PID partition** (`HKLM\SOFTWARE\Corsair\Corsair Utility Engine\CLinkPids` + `DevicesSharingService`) decides which product (iCUE vs standalone Link 4) may enumerate each PID. Nothing takes an exclusive HID handle. [OBS]
- Wire-format discrepancy to check before trusting: clink's PSU packet framing is `[0, addr<<1 | addr, cmd, arg…]`, ours (liquidctl style) is `[0, len, cmd, params…]`. See §3. [OBS, unreconciled]

### 2.2 Detection mechanisms (exact)
**A. WMI path (HidDevices module: PSUs, Coolit bridges, Robbins PSU)** — `HidDevicesCache` (`Core/HidDevicesCache.cs`):
1. `WhereFilter("DeviceID").StartsWith("hid")` → `ManagementObjectSearcher("root\CIMV2", "SELECT * FROM Win32_PnPEntity WHERE DeviceID LIKE 'hid%'")` (`Models/Device.cs` `[WmiClass("root\\CIMV2","Win32_PnPEntity")]`, `ManagementObjectEnumerator.Enumerate`). On exception: logs "Can't enumerate… Fix: set EnableEvents Key in registry to 1" and returns empty. [OBS]
2. `DeviceTypeResolver.GetDeviceType`: takes the substring after `"PID_"` in the PnP DeviceID (4 chars, lower-cased) and **hard-codes VID `1b1c`** (`CreateInstanceFromPid`) → `DeviceTypeDetector.GetDeviceType`. VID in the DeviceID is never checked. [OBS]
3. `DeviceFactory.CreateDeviceEntity`: `PowerSupply → PowerSupplyUnitDeviceEntity`, `Coolit → CoolitDeviceEntity`, `RobbinsPSU → RobbinsPsuDeviceEntity`, else `EmptyDeviceEntity` (dropped). [OBS]
4. Then `DevicesSharingService.Instance.IsAllowedToEnumerate(pid)` filter (see 2.5). Device path for opening is rebuilt from the PnP id: `\\.\` + `DeviceID.Replace('\','#')` + `#{HID-class-GUID}` (`HumanInterfaceDevice/DevicePathBuilder.cs`), not from SetupDi. [OBS]
5. Re-enumeration only on `OnDeviceArrival()` (and after firmware update); cache constructor arg 10.0 s is unused in the shown code (INF: refresh is event-driven). [OBS/INF]

**B. HidSharp path (Pro/Platinum modules: Commander Pro/Core-family, Lighting Node, Hydro/Elite coolers)** — `HidDeviceCachedProvider` (`Corsair.Module.Common`, not in the target list but needed):
- One static `HidDeviceLoader` (HidSharp), `validityPeriodMs = 900`, semaphore-guarded: if the cache is older than 900 ms, `loader.GetDevices(supportedDevicesCredentials)` and rebuild a `ConcurrentDictionary<devicePath, HidDevice>`; callers filter by `(VendorID, ProductID)`. [OBS]
- Provider diff loop (`PlatinumDeviceProvider.UpdateDevices`, `ProDevicesProvider.UpdateDevices`): `allDevices` vs tracked `devices` keyed by **DevicePath** → new paths → `InitDevice`, vanished paths → "Device was disconnected" + remove. A path that failed gets an `UpdateIgnoreTimeout` of **2 minutes** (`CanBeUsed`). [OBS]
- HidSharp opens with `EFileAccess.Read|Write`, `EFileShare.All` (`WinHidStream.cs:39`, `WinHidManager.cs:70`). [OBS]

**C. Hotplug (service level)** — `DeviceArrivalServiceBase`: `RegisterDeviceNotification(statusHandle, DEV_BROADCAST_DEVICEINTERFACE{dbcc_devicetype=5 (DBT_DEVTYP_DEVICEINTERFACE)}, flags=5)` (= `DEVICE_NOTIFY_SERVICE_HANDLE|DEVICE_NOTIFY_ALL_INTERFACE_CLASSES`, **no class GUID filter**). Handles `eventType 32768 (0x8000 ARRIVAL)` and `32772 (0x8004 REMOVECOMPLETE)`, only if `dbcc_devicetype == 5`, feeds an Rx `Subject` with `.Throttle(250 ms)` → `OnDeviceArrival()` → components re-enumerate. [OBS]

### 2.4 HX1500i / PSU: detection, identification, protocol (clink)
- **Detection**: PnP `DeviceID` contains `PID_1C1F` → `PowerSupply` → `PowerSupplyUnitDeviceEntity`. There is no probe/handshake needed to *classify* — the PID alone decides. [OBS]
- **Model identification (read after detection, informational)**: `UpdateInfo` runs `READ_MFR_ID (0x99)`, `READ_MFR_MODEL (0x9A)`, `READ_FIRMWARE_REVISION (0xD4)`; strings parsed by `BlockParser(7)` (ASCII from response byte 3, max 7 chars, NUL-terminated); FW by `FirmwareVersionParser` (response bytes 3..6 → `a.b.c.d`). The only regex model check, `^(HX|RM)\d+i$`, is for PSUs reached *through a Coolit bridge* (`CoolitDevice.CreatePSUCoolitConnectedPSU`, cmd 0x9A block of 7 via the bridge) — not for direct USB. Axion detection is PID-based (`1c24/1c25` → AX1300i/AX1600i, 10 PCIe OCP channels). [OBS]
- **Per-command flow** (`CommandStateMachine`, per command): `device.Open(ReadWrite)` (retried up to 5×) → build output report (`PsuOutputReportFactory`) → `stream.Write` (500 ms timeout via `TimingOutThreadRunner`) → `stream.Read` (500 ms) → `PsuResponseValidator` → extract. A **`HANDSHAKE` (0xFE) is sent before every command** (`DoRunCommand`: handshake, then command). [OBS]
- **Framing** (buffer length = `OutputReportByteLength`, bus address `1`): `buf[0]=0` report id; handshake: `buf[1]=0xFE, buf[2]=addr<<1 (=0x02)`; read: `buf[1]=addr<<1 (0x02), buf[2]=cmd`; write: `buf[1]=addr (0x01), buf[2]=cmd, buf[3]=arg` (two-byte args at 3..4). Response (stream read includes report-id byte): value LE at `[3],[4]`; error if `buf[2]==0xFE` (or `buf[3]==0xFE` when `buf[1]==0xFE`). [OBS]
- **PMBus command codes** (`PsuCommandCode`): PAGE 0x00, FAN_CONFIG_1_2 0x3A, FAN_COMMAND_1 0x3B, VOUT_OV/UV_FAULT 0x40/0x44, IOUT_OC_FAULT 0x46, OT_FAULT 0x4F, READ_VIN 0x88, READ_VOUT 0x8B, READ_IOUT 0x8C, READ_TEMP1/2 0x8D/0x8E, READ_FAN_SPEED_1 0x90, READ_POUT 0x96, READ_MFR_ID/MODEL 0x99/0x9A, READ_RUNTIME_TOTAL/NOW 0xD1/0xD2, READ_FIRMWARE_REV 0xD4, MFR_12V_OCP_MODE 0xD8, FAN_INDEX 0xF0, MFR_12VMON_INDEX 0xE7, MFR_READ_12V_IOUT/POUT 0xE8/0xE9, MFR_12V_IOUT_OC_FAULT_LIMIT 0xEA, …_ENABLE 0xEC, MFR_READ_TOTAL_POUT 0xEE, HANDSHAKE 0xFE. Page loop 0..2 = 12 V / 5 V / 3.3 V rails. Fan power written via `FAN_COMMAND_1` (percent byte) after mode change. [OBS]
- Parsing is `NumConverter.ToDouble((hi<<8)|lo)` (LINEAR11 decode in `NumConverter`; not decompiled further). [OBS]

### 2.5 Avoiding conflicts with other software
1. **Shared opens, not exclusive**: `HidDeviceManager.OpenDevice` → `CreateFile(path, GENERIC_READ|WRITE, FileShare.ReadWrite, …, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL)` (no overlapped); HidSharp `EFileShare.All`. Other apps (LibreHardwareMonitor, our app) can open the same PSU HID concurrently; the cost is interleaved request/response. [OBS]
2. **Short-lived handles**: handle is opened inside each `CommandStateMachine.Run`, and `PowerSupplyUnit.Dispose()` closes it after every sensor pass (`using PowerSupplyUnit psu = …` in `HidDevicesComponent`). [OBS]
3. **In-process serialization**: `CorsairThreadDevicesGuardLock` = static `SemaphoreSlim(1)` + `CorsairDevicesGuard.AcquireDevice/ReleaseDevice` executed on a dedicated `ThreadTaskScheduler` thread; wraps every device operation in `HidDevicesComponent`. [OBS]
4. **Cross-process mutexes**: `Global\Access_SMBUS.HTP.Method` (created with ACL for Everyone=Synchronize; this is the same name HWiNFO/CPU-Z/AIDA-style tools use for SMBus — INF), `Global\CorsairLinkSettingsProfilesMutex`, `GlobalReaderWriterLock` semaphores `Global\<name>_readerLock`. Service also releases the SMBus mutex on stop/shutdown. [OBS]
5. **Registry PID partition** (`DevicesSharingService`, key `HKLM\SOFTWARE\Corsair\Corsair Utility Engine`, value `CLinkPids` = `;`-separated hex ints, re-parsed on `ActualizeSharingSettings`). Logic: `isLink = process name starts with "CorsairLink4.Service"` (standalone Link 4). If `isLink`: allowed iff PID **not** listed. Otherwise (iCUE-hosted `Corsair.Service.exe`): allowed if PID ∈ `iCUEExclusives`, else allowed iff listed (prefix match). So iCUE publishes the PIDs it owns and the legacy Link service yields them. Observed value on this PC (read-only) contains e.g. `0xc3f 0x1c1f 0x1c27 0xc1c 0xc2a 0xc32 …` (≈150 entries). Writer of the value not located in any binary I scanned (INF: written by iCUE app/installer). [OBS value / INF writer]
6. **Update ignore timer**: failed device paths are skipped for 2 min (Pro/Platinum providers) to stop thrashing a device another app owns. [OBS]
7. **Fail-safe hooks**: components implement `SetAllFans100Percents` / `RestoreAllFansFromAlert` / `LimitedSoftwareMode` (RPC `LimitedSoftwareMode`, class `LimitedSoftwareModeSettings{device-id, enabled}`; `PlatinumXTDevice` gates software controls on it) and `DevicesSwitchHardwareLight`. Caller of `SetAllFans100Percents` on service stop is in `Corsair.Core` (not analysed). Relevant to the repo's open question on host-loss behaviour but only for legacy families; **no evidence about the iCUE LINK hub**. [OBS]

### 2.6 Device Control Service (real binary) and API
- Real service: `C:\Program Files\Corsair\Corsair Device Control Service\bin\CorsairDeviceControlService.exe` with `CorsairLLAccess{32,64}.sys`, `CorsairLLAccessLib64.dll` (`CrGetLLAccessInterface`), crashpad. SCM description: "Service for controlling CORSAIR devices by third-party clients". PDB path `Shared_Device_Service_master\…\CorsairDeviceControlService.pdb`. [OBS]
- Scope [OBS strings]: DRAM modules over SMBus (`SMBusGetControllers/GetCaps/Lock/Unlock/ReadByte/WriteByte/WriteWord/WriteBlock`, "Dram module … protocol v4", FW update, "Enabling DRAM HW lightings due to session end", `DramInternalPids`, `svc.dramctrl`, `svc.lla`). - IPC [OBS]: `CreateNamedPipeW/ConnectNamedPipe` on `\\.\pipe\CorsairUtilityEngine\<suffix>` (suffix built at runtime — not recovered), JSON (rapidjson) requests with `svc.server`, `svc.server.json`, `svc.server.rp`; client handshake with `clientId`, `clientProtocolVersion`/`serverProtocolVersion`; "Failed handshake / Rejected handshake for client"; "Registered new client with priority"; "Clients priority changed: reject control for {} and allow control for {}"; "Previous service session terminated incorrectly"; "Enabling DRAM HW lightings due to session end" (reverts to hardware lighting when the controlling client leaves). Uses `RPCRT4` only for GUID strings (`RpcStringFreeW`). [OBS]
- Conflict rule [OBS, decompile `FUN_14014bc10` @ 0x14014bc10, ev_b4d2bd0b]: builds a handle for service `"CorsairLLAService"`; if it exists, logs "CDCS execution not allowed due to conflicting service detected: …" and refuses to start. - API DLL exports/strings: `CDCSConnect/Disconnect`, `CDCSGetDeviceInfos`, `CDCSGetDeviceName`, `CDCSGetExtendedDeviceInfo`, `CDCSGetDramModuleData`, `CDCSSetLightingPriority`, `CDCSSubscribeToDevicesChanged`, `CDCSDeviceControlRequested`, `CorsairGetDeviceCount/Info`, `CorsairGetLedPositionsByDeviceIndex`, `CorsairGetLedsColorsByDeviceIndex`, `CorsairSetLayerPriority`; env `CDCS_DO_NOT_START_SERVICE_ON_CONNECT` (client auto-starts the service via SCM `StartServiceW` on connect). It also embeds a generic Windows-service host (CreateServiceW etc.). [OBS]
- Conclusion: DCS **does not** hold exclusive access to HID devices, does not broker USB HID, and is irrelevant to the HX1500i or the LINK hub. It is the SDK-facing arbiter for DRAM lighting. The 1.9.9 `.exe` in the iCUE folder is just its installer.

## 4. Recommendations (prioritized, Rust-implementable)
1. **Hotplug**: add a hidden message-only window (`windows` crate: `CreateWindowExW`, `RegisterDeviceNotificationW` with `DBT_DEVTYP_DEVICEINTERFACE` and the HID class GUID from `HidD_GetHidGuid`, handle `WM_DEVICECHANGE` `DBT_DEVICEARRIVAL/REMOVECOMPLETE`) or `CM_Register_Notification`; throttle 250 ms (tokio debounce) → `DeviceScanner::refresh()` → diff by `path`. Mirrors clink's design and replaces polling.
2. **Path-keyed device registry** with `HashMap<path, DeviceState>`; new path → init, vanished → drop; failed init → 2-minute backoff entry (clink `UpdateIgnoreTimeout`). Cache scans ≥ ~900 ms to avoid hammering `hid_enumerate`.
3. **Handle recycling / watchdog**: wrap HID write+read in a bounded timeout (spawn_blocking + deadline) and on timeout drop the handle and reopen (clink closes on any exception). Retry open up to 5× with short sleeps.
4. **Optional co-existence check** (read-only): at startup read `HKLM\SOFTWARE\Corsair\Corsair Utility Engine\CLinkPids` and the `CorsairService`/`CorsairDeviceControlService` states (`windows-service`/`OpenServiceW` query) and surface "iCUE service running — hardware shared" in the UI. Also consider acquiring/observing `Global\Access_SMBUS.HTP.Method` only if SMBus sensors are ever added; irrelevant for HID.
5. **Expand PID table** from §2.3 (HX/RM/AX PSU PIDs 1c03–1c27, AX dongle) — cheap, enables friendly names and future support; keep unknown-PID passthrough.
6. **PSU identity**: after init, read MFR_MODEL (0x9A, 7-byte block) + FW (0xD4) with the existing framing and log; if the model string does not match `^(HX|RM)\d+i$` warn. Needs hardware test (read-only commands).
7. **Do not** build around the DCS: nothing in it applies to HID. Only revisit if DRAM lighting (Dominator Titanium) is ever wanted — then the pipe protocol (`CorsairUtilityEngine`) and priority arbitration would be the integration point (protocol unreverse-engineered).
